# Local transcription

Movo transcribes a saved library recording with the installed Parakeet Ultra Q8_0 model. The engine selects the processing hardware automatically, and language behavior comes from the model. When speaker labels are turned on in Settings, it also labels who speaks when. It does not translate or call a paid API. Model installation and transcription are separate explicit actions.

## Processing

Before enqueueing, Movo checks the stored media, FFmpeg, the verified transcription model and, when speaker labels are on, the chosen speaker model in the existing Hugging Face cache. A missing or damaged speaker model is reported before the request is accepted, with guidance to download or repair it or to choose another option under **Speaker labels**. The job takes the speaker labels chosen at the moment it is queued, which for a download or import is after the recording is saved, and keeps them, so changing the setting later affects only new jobs and retries. Movo checks the resources again when execution begins. Missing or broken resources produce actionable errors; no model is downloaded or copied by a transcription request.

Downloads can also request transcription explicitly with **Transcribe after download**. FFmpeg and model availability are checked before accepting the combined request. The job uses the speaker labels chosen when the download completes; if they changed to a model that is no longer available by then, the job fails when it starts and reports why. Once the recording is saved, the download's completion and idempotent transcription enqueue share one SQLite transaction. Startup recovery uses the same operation when it finds a recording published by an interrupted download. The normal transcription worker handles execution, results and failures; the media and completed download remain available if transcription fails. Repeated download requests never replace or retry an existing transcription job.

FFmpeg selects the first audio track, resamples to 16 kHz mono and writes raw float32 audio to the job's temporary directory. Inputs are restricted to supported local file containers and the `file,pipe` protocol whitelist. A video with no readable audio track fails explicitly.

A separate Node process loads the model through `transcribe-cpp` and requests word timestamps. When the job uses speaker labels, the same process then releases the transcription model, runs speaker diarization on the same prepared audio and reports a separate **Identifying speakers** step. The engine passes the speaker model's verified files to the process by their role as one JSON argument, which the process validates. Sortformer runs through `transcribe-cpp` with its offline preset and labels up to four speakers. Pyannote runs through `sherpa-onnx-node`: the segmentation model finds speech and speaker changes, the embedding model describes each voice, and clustering groups the voices into speakers with a distance threshold of 0.5 instead of a fixed number of speakers; a larger threshold finds fewer speakers. If it finds more than 32 groups, the transcript's limit, clustering runs again with exactly 32. Pyannote runs off the worker's event loop and reports how many of its audio chunks have been described; the step shows that share as a percentage and a progress bar, saved in `transcription_jobs.phase_progress` and cleared when the step changes. Each word gets the speaker whose turns overlap it most, or the nearest turn for words in a gap, and speakers are numbered in order of first appearance. [Parakeet Ultra performs its own voice-activity segmentation for long recordings](https://github.com/handy-computer/transcribe.cpp/blob/main/docs/models/parakeet-ultra.md); Movo does not split audio at arbitrary time boundaries. Aborted or truncated output is rejected. The result is validated with Effect Schema, including word timestamps, word text without whitespace, words ordered by start time and word ends within the recording's duration plus a one-second allowance for model padding.

## Hardware selection

The worker loads the model with the engine's [automatic backend policy](https://github.com/handy-computer/transcribe.cpp/blob/main/bindings/typescript/README.md#backend-selection): the best accelerator supported by the installed native package, otherwise the CPU. The engine falls back to the CPU without an error when, for example, the Vulkan loader or driver is missing. Movo does not add its own fallback or offer a device setting. A failure to initialize or run on the selected device fails the job and publishes no transcript.

After loading, the worker reports the device the model actually runs on. The job stores it as `device` with the engine's backend (`cpu`, `vulkan`, `cuda`, `rocm` or `metal`) and the device name. The recording page shows it while the job runs and after a failed attempt, and **History** lists it with the transcription result; a CPU fallback therefore appears as the CPU. Failed, cancelled and interrupted attempts keep the device they ran on. Retry and re-transcription clear it until the next attempt reports one, so the device always describes the latest attempt. Transcripts completed before this field existed have no device. A worker result without a device report is rejected.

The model worker is connected to its backend through Node IPC and exits if the owner disappears. Cancellation and ordinary shutdown stop the owned process before removing its temporary files. This is process isolation for lifecycle and fault handling, not an operating-system security sandbox.

## Storage and lifecycle

The `transcription_jobs` table in `MOVO_DATA_DIR/app.sqlite` stores one job per media ID, the model ID, the speaker model chosen when the job was queued or retried (`speaker_model_id`, empty when speaker labels were off), the speaker model that labeled the saved transcript (`result_speaker_model_id`, set in the same update that saves it and empty when the transcript has no speaker labels, such as a recording without speech, so a running or failed attempt with other speaker labels does not change it), state, the current step and its progress, timestamps, errors and the completed transcript. The transcript stores the recognized words, each with `startMs`, `endMs`, `text` and, when speakers were identified, a numeric `speaker`, plus a nullable detected language and optional `speakers` names. Passages are derived from the words wherever they are shown or exported, so their rules can change without transcribing again. Library search keeps its own copy of each transcript's passages together with the names given to their speakers, so a search for a name finds that speaker's passages; numbered speakers without a name are not searchable. Renames, speaker changes and every other transcript change update that copy. A change to the passage rules must raise `searchIndexVersion` in `src/server/media/search.ts`, which makes Movo rebuild the search index at its next startup. A unit test pins the passages of a sample transcript to the current version and fails until the version is raised. A migration discards transcripts saved before word timestamps: their jobs become failed with an explanation, so the recordings can be retried and startup still cleans their temporary files. Native model output that does not provide a language leaves it unset. Output with no recognized text or words completes with an empty transcript, whatever timestamp kind the engine reports for it; recognized text or words without word timestamps fail the job.

Work files live in `MOVO_DATA_DIR/transcriptions/<media-id>/`. Stored library media and shared Hugging Face weights are read-only during transcription. Results become visible through one database update; partial inference is not published as a completed transcript.

Jobs move through queued, running, completed, failed, cancelled or interrupted states. A single worker runs one transcription at a time, independently of media downloads and browser requests. Duplicate enqueue requests return the existing job. Cancel and retry operations are serialized so concurrent requests cannot clean files belonging to a new attempt.

**Transcribe again** starts a new attempt for a completed recording through the retry operation. The row keeps its last successful transcript while the new attempt is queued or running, and the panel shows it with a note until a replacement completes. A successful attempt replaces it, and discards its edit history, in the same update that marks the job completed. It is in the recording's **More actions** menu, where it opens a **Speaker labels** choice for this attempt: **Up to 4 speakers** (Sortformer), **Up to 32 speakers** (Pyannote) or **No speaker labels**, so a recording that needs a different speaker model can be transcribed again without changing Settings. Speaker models that are not installed are shown as **Not installed** and cannot be chosen. When the transcript has been edited, each choice first asks for confirmation. **Retry transcription** after a failed attempt and retries from the library use the speaker labels chosen in Settings. Failure, cancellation and interruption keep the previous transcript. After a failure or interruption the panel reports the new attempt's state and error and notes that it shows the previous transcript; after a cancellation it simply shows that transcript, without a note. A second retry while an attempt is queued or running is rejected, so one recording never has two active attempts.

Startup marks persisted running jobs interrupted and clears terminal staging directories. Queued jobs continue automatically. Interrupted jobs require an explicit retry; both keep any previous transcript. Cleanup failures are saved separately on the affected job and do not stop other recordings or discard a completed transcript. Retrying requires successful cleanup. Restart attempts cleanup again.

## Passages and reading along

`src/shared/transcript-passages.ts` groups words into passages. A passage ends after a word that ends a sentence (`.`, `?`, `!` or `…`, optionally followed by closing quotes or brackets). Common English abbreviations that precede more text, such as `Mr.`, `Dr.`, `St.`, `e.g.` and `vs.`, do not end a sentence; abbreviations that often close one, such as `a.m.`, `U.S.` and `Jr.`, still do. A sentence longer than 84 characters or 7 seconds, the length of a two-line subtitle, is split in two until every part fits. Each split uses the `,`, `;` or `:` closest to the middle when one lies in the middle half of the text; otherwise it uses the word boundary closest to the middle, so no short remainder is left behind. A single word longer than either limit forms its own passage. A silence of 3 seconds or more between two words, or a change of speaker, also ends a passage. Shorter pauses are not used: the model reports only long silences as gaps between words and usually adds shorter pauses to a neighboring word. The model's own long-form segments are internal processing chunks of up to 30 seconds and are not used for display.

While the recording plays, the passage containing the current word is highlighted and marked with `aria-current="time"`, and the current word is wrapped in `<mark>`. The current word is the last word that started at or before the player's position. Only the passages whose state changes re-render. Word timestamps come in 80 ms steps and can be off by a word or two; selecting a passage's timestamp seeks to its first word.

The navigation and the transcript tools never leave the screen; only the transcript scrolls. The tools row, with **Ask** at its right end, is there in every state, so nothing moves when a transcript arrives: before transcribing it holds only **Ask**, and the card that starts or follows the transcription sits where the passages will appear, level with the top of the video. On a screen at least 1024 px wide, or 1248 px while Ask is open, the recording page splits in two: the back link, player, title and details stay pinned in a column beside the transcript, and an audio recording's player sits in that column instead of floating at the bottom. On a narrower screen the page is one column: the header (from 640 px), the back link and the transcript tools stay pinned, and once a video scrolls out of view a compact player with play, position and **Show the video** takes its place above the tools. **Show the video** scrolls back to it, moves focus to the video player and stops following, so **Back to current** returns to the passage being spoken. Opening Ask keeps the recording in view: it narrows the video column, or below 1248 px falls back to the single column, where a floating audio player stays centred beside the panel. When a new passage starts, the page scrolls it to just below the transcript tools, leaving the end of the previous passage visible. Scrolling by hand with the wheel, middle-button autoscroll, touch, keyboard or scrollbar stops this, and **Back to current** brings the passage being spoken back into view; seeking also resumes following. Following is suspended while a passage is being edited or **Find and replace** is open, but choosing a moment link still scrolls to its passage; if the passage being spoken is off screen when they close, following stays paused and **Back to current** appears. Following scrolls instantly instead of smoothly when the system asks for reduced motion.

A video with a saved, nonempty transcript also shows it as subtitles: one cue per passage in a `Transcript` subtitle track, shown by default on screens at least 640 px wide, hidden by default on narrower screens, and toggled through the player's caption control. The browser builds the track from the transcript it already loaded, using the same WebVTT text as **Download VTT**, so no extra request is made. When a new transcript completes, the track's content is replaced and the viewer's subtitle choice is kept. Audio recordings have no subtitle track.

## Copy and export

Saved, nonempty transcripts show **Copy transcript** and **Export transcript**, which offers **Download TXT**, **Download SRT** and **Download VTT**, above the passages. Copying and TXT use the same plain text, one passage per line. Downloads use UTF-8.

Below the downloads, the export menu chooses what the text carries, and the same choice applies to copying and to every download. **Speaker names**, shown only when the transcript has speaker labels, places names **At each turn** (the default), **On every line** or nowhere (**Off**). On every line names each plain-text passage and SRT cue rather than only the first of a turn; WebVTT marks every cue with its voice in both placements. **Timestamps in TXT** is off by default; turning it on starts each plain-text passage with its start time as `[hh:mm:ss]`, before any speaker name. SRT and WebVTT always carry cue times. The browser remembers the choice locally and shares it with other open tabs; when storage is unavailable, the choice lasts until the page reloads. The server supplies the recording title with the selected extension in `Content-Disposition`, so normal links and direct export URLs use the same filename. The header includes an ASCII `filename` fallback and UTF-8 `filename*`; path separators and control characters are replaced with underscores.

When a transcript has more than one speaker or a named speaker, copying and TXT start each speaker's turn with its name, or `Speaker` and its number, and separate turns with a blank line. SRT starts the first cue of each turn with the name, and WebVTT marks every cue with a `<v>` voice span.

SRT and WebVTT export one subtitle cue per passage with millisecond timestamps. Words never contain whitespace, so a cue cannot be split by blank lines. Subtitle text escapes `&`, `<` and `>` so recognized text remains literal. Existing overlaps are preserved. A zero-duration passage receives a one-millisecond cue so its text is retained with a valid end time. See the [SubRip description](https://www.loc.gov/preservation/digital/formats/fdd/fdd000569.shtml) and [WebVTT specification](https://www.w3.org/TR/webvtt1/).

Exports read the saved result on demand. They do not start inference, require an installed model, write additional managed files or modify the stored transcript. The empty-speech message has no copy/download actions; the API can still export that completed empty result. Without speech, the recording page also leaves out **History** and **Remove saved copy**, and Ask explains that there is nothing to ask about; **Transcribe again** stays available. A transcript whose passages were all removed by edits keeps **History** and **Remove saved copy**, and Ask points to restoring a version.

Copying runs only after an explicit action using the browser's Clipboard API. A denied or unavailable clipboard produces an error with permission guidance and the TXT alternative; it never reports success before the write finishes. Browser API reference: [Clipboard.writeText](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard/writeText).

## Resource use

Decoded float32 mono audio uses 64,000 bytes per second, approximately 230 MB per hour on disk. The isolated worker reads that prepared audio into memory, in addition to the model and inference workspace. Longer recordings therefore need proportionally more free memory and disk space. The worker reads the file in chunks, so Node's 2 GiB whole-file read limit does not apply. The engine accepts at most 2³¹−1 samples (about 37 hours); longer recordings fail before the audio is loaded. Preparation has a 30-minute timeout and inference a six-hour timeout. Memory allocation or native runtime errors fail the job; they do not silently publish partial text.

The initial implementation keeps native long-form segmentation and does not add a custom streaming decoder. Speaker identification keeps the prepared audio in memory while the speaker model runs and adds its processing time to the job. Manual device selection, recognizing the same person across recordings and keeping several transcription results of one recording are outside this implementation.

## Searching a transcript

**Search** above the transcript finds the passages that contain every searched word, in what was said or in the speaker's name. Words match like library search: by their beginning, ignoring case and accents. Matching words and names are highlighted, the counter shows the current match, and the arrow buttons, Enter and Shift+Enter move between matches; the current passage is tinted and scrolled into view. When a matched name has no heading because the speaker's turn started earlier, it is shown next to the passage time. Search is available whenever the transcript has words, also while a new transcription runs. Search and **Find and replace** share one bar that takes the place of the transcript tools: its **Search** | **Replace** switch shows which one is open, moves between them and carries the typed text over, and **Close** or Esc brings the tools back and returns focus to the button that opened the bar. Ctrl+F (⌘F on a Mac) opens search or switches the bar to it, and pressing it again while the search field has focus leaves the browser's own find; Ctrl+H (⇧⌘H on a Mac, where ⌘H hides the browser) opens **Find and replace** or switches the bar to it. Text carried over to search is cut to the 200 characters a search query can hold. The toolbar shows each key with its platform's modifier. With speakers chosen in **Speakers**, search covers only their passages and its placeholder says so. The arrow buttons name their keys in a tooltip. The query is kept in the recording's `q` address parameter, so it survives reloads, and **Search in this recording** in library search results opens the recording with the library query when more passages contain every word than the result shows. A match object reports both `passageCount`, the passages with any searched word, and `everyWordPassageCount`, the passages with every word, because a recording also matches when its words are spread over its title, passages and speakers.

## Showing chosen speakers

When the transcript has at least two speakers, **Speakers** after **History** shows only the passages of the speakers ticked in its menu, listed in the order they first talk. The menu stays open while several are ticked, and **Show everyone** clears the choice. The button shows the chosen speaker's name, or how many are chosen, and stays tinted while the choice applies. Each turn of another speaker folds into one row with its passage count and time range; clicking the row opens those passages in place, where they can be played from and edited like any other, and clicking it again folds them. A turn with a passage being edited stays open until the edit is saved or cancelled, even when its speaker is unticked. A moment link into a folded turn opens it. When playback reaches a folded turn, its row is tinted and the transcript follows it.

**Play only these speakers** in the same menu makes playback jump from the end of a chosen turn to the next one, also after seeking into someone else's turn, and pause after the last chosen turn; playing again from there starts at the first one. The position slider marks the chosen turns, the player says whose turns play, and folded rows say they are skipped. Clearing the choice turns it off.

The choice also scopes the other transcript tools: search and **Find and replace** cover only the chosen speakers' passages, the notification after **Replace all** names them, and **Copy** copies only their passages. Exports keep the whole transcript. The choice is kept in the `speakers` and `only` address parameters, so it survives reloads.

## Editing

A saved transcript can be corrected without transcribing again. Every change is saved as a new version with its own history, and any earlier version can be restored. Exports, copying, search, reading along and MCP always use the current version.

- **Edit passage** (the pencil next to each passage) opens its text in a text field. Ctrl+Enter or **Save passage** saves it, and Esc or **Cancel** discards it. Clearing the text removes the passage. Saving may split or join passages, because passages are derived from the edited words.
- **Find and replace** replaces every whole-word match of a word or phrase. Matching ignores case but not accents, so `zolw` does not change “żółw”. Punctuation around a match is kept: replacing `kubernetis` with `Kubernetes` turns “Kubernetis,” into “Kubernetes,”. A phrase can span several words, and an empty replacement removes the matches. Before anything is saved, the form highlights the matches in the transcript and counts them, and the arrow buttons or Enter step through them, using the same code that applies the change on the server. The form stays pinned above the transcript while it scrolls to each match. A match never runs from one speaker's words into another's, so a replacement cannot move words between speakers. With speakers chosen in **Speakers**, only their words are found and replaced. After **Replace all**, a notification counts the replacements and its **Undo** restores the version before them.
- **Speakers**: when speakers were identified, each speaker's turn starts with its name, even when only one speaker was found, so that speaker can be named too. Its menu names the speaker for the whole transcript or merges it into another speaker, and the button next to **Edit passage** moves a passage to another speaker or a new one. Moving and merging are saved as versions; names are kept separately, apply immediately, make that speaker's passages searchable by name and do not change the version.
- **History** lists the versions, newest first, with the first changed text of each and whether an AI agent made it over MCP. It opens as a side panel. **Restore** returns to a listed version, including the transcription result at the bottom of the list. A restore is itself a new version, labelled with the change it went back to, so it can be undone as well. Restoring again right after a restore replaces that restore instead of adding another one, and restoring the version just before a restore removes it, so trying out versions does not clutter the history. Edits are never removed. Restoring a version with the same text as the current one changes nothing. The newest entry is always the current version.

Words keep their timestamps whenever an edit leaves them in place. Unchanged words at the start and end of an edited passage keep theirs. When the number of words stays the same, each new word takes the timestamps of the word it replaces. Otherwise the new words share the time span of the words they replace, in proportion to their length, and inserted words without a replaced word fall in the gap between their neighbors. Words stay ordered by start time, and the result passes the same schema as engine output.

Editing is rejected while a new transcription attempt is queued or running, because its result would replace the edits. Every change names the version it was made from; a change based on an older version is rejected with HTTP 409, and the browser reloads the transcript. An open passage editor keeps its text, shows what the passage now reads and saves the text over the current passage only after **Use my text for the current passage**.

Version numbers never repeat for a recording. Each saved change and each completed transcription attempt takes the next number, so a change prepared against a transcript that was later transcribed again is rejected rather than applied to different words. A first transcription result is version 1.

A change that would make the transcript longer than 1,000,000 words, the limit for engine output, is rejected with HTTP 400.

The current transcript stays in `transcription_jobs.transcript`. `transcription_jobs` also stores `revision`, the current version, and `result_revision`, the version of the latest transcription result. The `transcript_changes` table stores one row per version after that result, with its kind (`edit`, `replace`, `speaker`, `dictionary` or `restore`), source (`app` or `mcp`), the restored version and the replaced words. Each change is a list of replacements, each with the position, the removed words and the inserted words, so a change takes about as much space as the text it touches rather than a copy of the transcript. Restoring applies the stored changes backwards, verifying that every removed word is still in place, and saves only the net difference between the current and restored words, so repeated restores do not grow the history. A restore that directly follows another restore deletes that restore's row and stores its own difference from the version before it, or no row when that version is the target. `revision` still increases, so a version number is never reused. The transcript, its change and the search index are updated in one SQLite transaction. Deleting a recording deletes its history.

## Dictionary

The dictionary holds names and words Movo spells your way. It is managed from **Settings → Transcription → Dictionary → Manage**, a dialog that lists the entries and opens one at a time. Each entry has:

- **Spelled**: the form it should read. It always matches whole words or phrases ignoring case, so `movo` and `MOVO` become “Movo”. Punctuation around a match is kept, as in **Find and replace**.
- **Similar spellings**: off for a new entry. When turned on, it also matches spellings that differ by letters, compared without case or accents and also across two neighboring words joined (`para keet`). Words of 4 letters or fewer cannot use it, because one letter would already turn ordinary words into the entry; 5–7 letters allow one difference and 8 or more allow two (insertion, deletion, substitution or swapped neighbors). Words are never joined across punctuation. It starts off because one letter also separates ordinary words from a name, such as "codes" from Codex, and those changes would land in new transcripts unseen; the preview shows what it would fix before it is turned on for good.
- **Also replace**: words or phrases the model hears differently, such as `cloud code` for “Claude Code”, matched exactly ignoring case.
- **Never change**: words or phrases the entry leaves as heard. The entry changes no word inside them, even when a single word of a phrase would match. Like the phrases it replaces, a phrase only counts when punctuation does not split it, so `parakit. Bird` is not the exception `parakit bird`.

When entries compete for the same words, exact matches win over similar ones, then the longer phrase, then the closer spelling, then the spelling that comes first alphabetically, so the preview and the fix always pick the same entry. A similar spelling never changes a word that is itself an entry's spelling. A longer phrase listed under **Also replace** still can: with entries `Cloud` and `Claude Code` listing `cloud code`, "Cloud code" becomes Claude Code, because that phrase was listed on purpose. Each word is changed at most once, so one fix never triggers another. A spelling or phrase can belong to only one entry; Movo rejects a clash and names the entry that already has it.

Every completed transcription, including **Transcribe again**, applies the dictionary in the same database update that saves the result. The fixes form their own version, “Dictionary fixed …”, after the transcription result, so **Restore** brings back the model's words. Each entry counts the words it has fixed.

Changing the dictionary does not rewrite existing transcripts by itself. While an entry is open, **Already in your library** previews its matches in saved transcripts, with a few words of context. Each match can be unticked to leave it as heard. **Save** stores the entry for new transcriptions only; **Save and fix N recordings** also applies the ticked matches, each recording as its own **Dictionary** version. A recording that changed after the preview, or whose new transcription is queued or running, is skipped and named in the confirmation; a new transcript uses the dictionary anyway. Removing an entry keeps the words it already fixed.

Entries are stored in the `dictionary_entries` table of `app.sqlite`. Matching lives in `src/shared/transcript-dictionary.ts` and runs on this computer; no model is involved.

## HTTP interface

All commands use the existing local-origin checks. They operate on a saved media ID and take no JSON options.

- `GET /api/media/:id/transcription` returns the job or `null` when the media exists without a transcription. Responses use `Cache-Control: no-store`.
- `GET /api/media/:id/transcription/export/:format` downloads the saved transcript, including while a replacement attempt runs or after it fails, as `txt`, `srt` or `vtt`. The optional `speakers` query value `turn`, `line` or `off` places speaker names, and `timestamps` of `true` or `false` adds plain-text times; they default to `turn` and `false`, and any other value returns HTTP 400. Responses use the corresponding content type, `Content-Disposition: attachment` with the filename parameters above, `Cache-Control: private, no-store` and `X-Content-Type-Options: nosniff`. Unsupported formats and recordings without a saved transcript return HTTP 400. No transcription is enqueued by this request.
- `POST /api/media/:id/transcription` returns HTTP 202 with the existing or newly queued job.
- `POST /api/media/:id/transcription/cancel` returns the current job after stopping active work, or `null` when none exists.
- `POST /api/media/:id/transcription/retry` returns HTTP 202 after starting a new attempt for a completed, failed, cancelled or interrupted job. Queued and running jobs are rejected. An optional JSON body `{ "speakerModelId" }` of at most 4 KiB chooses speaker labels for this attempt, a speaker model ID or `null` for none; without it the attempt uses the speaker labels chosen in Settings. A chosen speaker model that is missing or damaged is rejected before the attempt starts.
- `POST /api/media/:id/transcription/edit` replaces words with JSON `{ "revision", "firstWord", "wordCount", "text" }`.
- `POST /api/media/:id/transcription/replace` replaces matches with JSON `{ "revision", "find", "replacement" }`.
- `POST /api/media/:id/transcription/restore` returns to an earlier version with JSON `{ "revision", "target" }`.
- `POST /api/media/:id/transcription/speakers/assign` moves words to a speaker with JSON `{ "revision", "firstWord", "wordCount", "speaker" }`; `speaker` is an existing number or the next unused one.
- `POST /api/media/:id/transcription/speakers/merge` moves every word of one speaker to another with JSON `{ "revision", "speaker", "into" }`.
- `POST /api/media/:id/transcription/speakers/rename` names a speaker with JSON `{ "speaker", "name" }`; an empty name removes it. Names have at most 80 characters and do not change the `revision`.
- `GET /api/dictionary` lists the dictionary entries. `POST /api/dictionary` adds one and `PUT /api/dictionary/:id` replaces one, both with JSON `{ "draft", "fix" }`: `draft` is `{ "spelling", "similar", "alsoReplace", "neverChange" }` with words or phrases of up to 100 characters and lists of up to 50, and `fix` lists the recordings to fix as `{ "mediaId", "revision", "skip" }`, where `skip` holds the first word of each unticked match. They return the entry, the fixed word and recording counts and the skipped recordings with a reason. `POST /api/dictionary/preview` takes `{ "id", "draft" }` and returns the matches in saved transcripts, up to 200 shown, with their total. `DELETE /api/dictionary/:id` removes an entry. Dictionary bodies are limited to 1 MiB, enough to fix about 13,000 recordings at once; clashing or invalid entries return HTTP 400 and unknown entries HTTP 404.
- `GET /api/media/:id/transcription/changes` lists versions newest first with the optional `limit` (1–100, default 20) and `offset` query parameters and the `total`.

Job responses include `revision`, the current version number, and `resultRevision`, the version of the transcription result; the transcript is edited when `revision` is greater. They also include `speakerModelId`, the speaker labels of the current or latest attempt, and `resultSpeakerModelId`, the speaker model that labeled the saved transcript. The recording page shows the latter under the title next to the transcription model, for example **Parakeet Ultra · Pyannote speaker labels**, and in the details of the transcription result in the history. A restore `target` must be `resultRevision` or a version listed in the history. Each listed restore reports in `restoredRevision` and `restored` the edit, or the transcription result when `restored` is null, whose text it brought back. The change commands return the job after the change, or unchanged when nothing changed. They accept bodies of up to 64 KiB, edit text of up to 10,000 characters and find or replacement text of up to 512 characters, with words of up to 1,024 characters. Without a saved transcript or for a version or word range outside it they return HTTP 400; for an older `revision` or while a new attempt is queued or running, HTTP 409. Request and response shapes are the Effect schemas in `src/shared/contracts/transcriptions.ts`.

An invalid or missing media ID returns HTTP 404. Model/tool unavailability returns HTTP 503. The worker owns accepted work after the initiating request ends.

## Verification

Normal tests use real temporary SQLite and filesystem storage, real local FFmpeg conversion and controlled substitutes only at inference/process boundaries. Browser tests verify explicit initiation, setup errors, navigation during work, cancellation/retry, re-transcription with the previous transcript visible, saved passages, reload, empty output, seeking and the highlighted passage and word, the video beside the transcript and the compact player on a narrow screen, following the spoken passage, pausing on a manual scroll and returning with **Back to current**, and the search and replace shortcuts. They never download weights or inspect the user's model cache.

Editing tests cover timestamp reuse and redistribution, insertion, removal, overlapping words, whole-word and multi-word matching with punctuation and accents, and that undoing every change returns the original words. Storage tests use real SQLite for edits, replacements, restores, stale versions, versions that would repeat after transcribing again, restore history size, edits during a new attempt, search updates and deletion with history; browser tests edit with the keyboard, keep a draft through a conflicting change, preview and apply replacements, undo and restore versions and confirm transcribing again.

Export tests cover literal text, Unicode, millisecond/hour boundaries, overlaps, zero-duration cues and empty results. HTTP tests exercise real saved transcripts and reject exports before completion. Browser export tests use an isolated real backend and database with a controlled inference result, save all three formats, parse the exported WebVTT with Chromium, and verify keyboard actions, narrow layout and clipboard failures. Clipboard tests replace the browser API without changing the system clipboard.

`bun run test:transcriptions:real` is an opt-in test requiring FFmpeg, FFprobe and the pinned model already installed in the configured Hugging Face cache. It never downloads or modifies weights. It transcribes a small synthetic speech fixture, repeats it locally to exercise native long-form segmentation beyond 30 seconds, checks recognized words and timestamp offsets, requires an accelerator to be selected when the engine reports one and the CPU otherwise, and removes its isolated library and prepared audio. Existing `HF_HUB_CACHE`, `HF_HOME` and `XDG_CACHE_HOME` settings select the cache as usual.
